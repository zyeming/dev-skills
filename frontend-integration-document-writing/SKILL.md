# 前端接入文档编写

## 目标与边界

创建或维护一份可供前端工程师直接接入后端能力的 Markdown 文档。文档必须回答：调用哪些 API、怎样传参、返回什么、哪些内容新增或变化、何时调用、失败后怎样恢复，以及新旧版本如何兼容。

接入文档描述对前端可观察的契约和行为，不展开数据库、SQL、Mapper、内部类、模块间 DTO 传递或事务实现。原子性、幂等、通知是否送达等会改变前端处理方式的结果仍属于外部行为，应明确说明。

## 工作模式

- **新建**：从需求、设计、实施方案和当前代码生成新的接入文档。
- **更新或精简**：把最新契约更新到唯一归属位置，删除失效或重复内容，保留既有有效结构。
- **评审**：检查遗漏、歧义、冲突和不可执行内容；用户说“先别写”“只看一下”时只报告，不修改文件。

用户指定目标文件和只读参考时，只修改目标文件。文档格式、路径和命名优先遵守项目 `AGENTS.md`、`CLAUDE.md` 和既有约定。

## 事实来源

先区分当前契约和目标契约，不给任何单一文档无限权威：

- 用户最新确认、已批准需求和已确认设计决定目标行为。
- 当前 Controller、路由、请求/返回类型、枚举、校验和实际调用方决定当前行为。
- Technical Design、Implementation Plan 和发布说明用于描述目标契约、实施修正和版本边界；`Draft` 只作为参考。
- 现有接入文档用于复用术语、结构和重要不变项，不能覆盖当前代码或最新目标决定。

源码尚未实现目标变化时，不用当前代码否定已经确认的目标契约。文档描述的当前行为与源码冲突时，以源码为准。目标资料之间出现字段类型、脱敏、权限、状态、兼容或发布结论冲突时，必须报告“契约冲突”；没有明确依据时不得按文件日期、个人偏好或猜测静默选择。

## 工作流程

1. 读取项目规则、用户指定资料、目标文档和必要的现有接入文档。
2. 定位真实 HTTP 入口、公开请求/返回类型、枚举、公共响应包装和前端调用方；只调查与本次接入直接相关的代码。
3. 建立内部 API 变化表，逐项标记：新增、变化、语义变化、不变、废弃。
4. 分开整理当前与目标的请求字段、返回字段、调用时机、状态、错误、兼容和发布依赖，解决或显式记录来源冲突。
5. 新建或重组文档时完整读取 [前端接入文档模板](references/frontend-integration-document-template.md)。模板是候选结构，没有信息价值的章节删除。
6. 每个 API 按本技能的契约要求写清输入、输出和前端处理；共享对象只定义一次后引用。
7. 评审和交付前完整读取 [Review Checklist](references/frontend-integration-document-review-checklist.md)，先补完整性，再删除重复和实现噪音。
8. 检查 Markdown、本地链接、字段名、方法和路径；只改文档时不运行业务代码测试。

## API 契约要求

### 变化总览

文档开头用一张表覆盖全部受影响接口，至少区分：接口类型、方法与路径、请求变化、响应变化。结构不变但权限、过滤、排序、状态、副作用或成功含义变化时，标记为“语义变化”，不能归为不变。

明确列出新版前端不应继续使用的旧路径、旧字段、错误大小写、旧枚举或兼容参数。没有废弃项时不创建空清单。

### 完整输入与输出

接入文档必须能够独立使用：

- 每个 API 写明方法、路径、鉴权方式和参数位置。
- 请求字段写明字段路径、实际 wire 类型、必填或条件必填、默认值、允许值、长度或数量限制及变化属性。
- 响应字段写明实际 wire 类型、是否必返或可空、条件返回、顺序和变化属性。
- 现有接口也要列出前端仍需使用的完整直接业务字段，并逐项标记“不变”或“变化”；不得用没有文内稳定引用的“其他字段不变”代替。
- 多个接口共享大型对象时，只完整定义一次，其他接口引用对应章节并单独说明差异。
- 公共响应包装只定义一次；错误码、时间格式、空数组和 `null` 规则没有证据时不要编造。

请求和响应示例用于说明容易误用的完整组合，不为每个简单接口机械生成示例。示例使用占位 ID，不出现真实患者信息、Token、手机号、密钥或生产域名。

## 前端必须知道的行为

只在与本次能力相关时检查并说明：

- 不同端、入口、路由或 Scheme 应使用的 API、业务类型和上下文字段。
- 名称相近字段、不同 ID、大小写、Query/Path/Body 位置及旧字段兼容。
- 分页、加载更多、搜索口径、排序、跨页选择、去重和返回顺序。
- 服务端返回的状态、权限和 `can*` 字段；前端不得用本地缓存、时间或通知已读状态覆盖服务端事实。
- 首次进入、内容成功渲染、页面重新可见、主动刷新和状态操作成功后的调用顺序。
- 超时能否重试、接口是否幂等、状态冲突后刷新什么、失败时保留哪些本地输入。
- 成功究竟表示创建、受理、提交、送达、已读还是完成，避免把不同成功口径混用。
- 历史数据、旧客户端、混合版本、后端前置版本、动态页面和发布顺序。

不要展开组件结构、视觉样式、按钮位置、表单布局或普通交互细节。只有交互动作决定 API 参数、调用时机、状态或失败恢复时才说明。

## 结构与表达

- 按前端理解任务的顺序组织：公共约定与变化总览 → 公共类型 → API → 调用流程 → 异常与兼容 → 联调检查。
- 多端能力差异明显时按端或业务流程分组；接口高度共享时按能力分组，不机械拆成重复章节。
- 字段和固定映射使用表格；有先后关系的调用使用编号列表或短文本流程；只有复杂分支明显降低理解成本时才使用图。
- 同一字段、状态或规则只完整定义一次。表格已经说明的内容不在下文逐行复述，只补前端动作和例外。
- 简洁不等于只列变化字段。优先保留完整契约、条件返回、调用时机、失败恢复和兼容边界，再删除调查过程、后端实现和重复说明。

## 输出与停止条件

项目有文档目录和编号规则时严格沿用；否则默认输出到：

```text
docs/frontend-integration/{ticket-id-or-feature-name}.md
```

交付时说明创建或修改的目标文档、已验证内容和仍未解决的契约冲突。完成文档后停止，不继续修改前端或后端代码，也不发布服务，除非用户明确要求。

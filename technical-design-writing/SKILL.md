# Technical Design 编写

## 目标与边界

为单个具体软件需求编写一份供熟悉项目的人评审和决策的技术设计。文档要同时满足三点：

- 架构合理：业务目标、领域边界、模块职责、依赖方向和数据流清晰，支持长期维护和持续演进。
- 契约准确：数据模型、DDL、API 字段、服务归属和兼容边界可以直接用于评审。
- 实现简洁：内部实现只保留责任、行为和关键约束，不搬运源码调查过程。

Technical Design 承载本次需求的架构决策、技术契约和实现约束。长期架构文档与 ADR 记录跨需求持续有效的决策。默认状态为 `Draft`；只有用户或项目流程明确确认后才标记为 `Approved`。

## 选择工作模式

先根据用户要求选择一种模式：

- 新建：从需求和现有实现起草新的 Technical Design。
- 修改：在指定文档中更新、补充、精简或重组内容。
- 只读评审与答疑：分析设计、核对源码或回答问题，不修改文件。

用户明确“先别改”“只看一下”“先确认”时，固定使用只读模式。同时提供多个文档时，先区分目标文档和只读参考；只修改用户明确指定的文件。

需求语义、范围或验收标准不清楚时，转 `$requirements-clarification`。可安全推断但尚未证实的内容标记为 `假设：`，不要写成事实。

## 事实来源

按以下优先级核实设计：

1. 当前用户指令和已经确认的需求。
2. `AGENTS.md`、`CLAUDE.md` 和仓库规则。
3. 当前源码、配置、DDL、schema 和测试。
4. 架构文档、ADR 和用户指定的参考方案。
5. 外部官方文档。

源码和运行配置决定系统当前行为。与说明文档冲突时，以源码为准并指出文档漂移。不要根据需求设想编造现有类名、方法名、字段类型或处理流程。

## 工作流程

1. 锁定目标和边界：确认目标文件、只读参考、本期技术变化、关键复用、必要设计边界和用户是否允许修改。
2. 建立内部变化清单：盘点数据模型、页面、API、Facade、事件、定时任务、配置、发布与回滚，只纳入直接变化或构成旧数据、旧客户端、旧调用方兼容条件的内容。
3. 核实现状和同类实现：定位真实应用、入口、契约和数据所有权；对新增或职责变化的能力，核对同一应用中最接近的现有实现。调查可以深入，成稿不记录调查流水账。
4. 先确定目标架构，再收敛本期方案：根据业务目标和领域规则明确模块职责、依赖方向、数据所有权和数据流。复用合理的现有边界；需要调整时说明理由、影响和迁移路径。按下方架构质量要求检查方案，只引入真实用例所需的实现。
5. 按 `references/technical-design-template.md` 起草或重组文档。修改已有文档时，在原责任章节更新并删除失效内容，不追加孤立的补充说明。
6. 做完整性检查：使用 `references/technical-design-review-checklist.md` 核对架构质量、API、字段、DDL、服务归属、前端体验、验证、观测、兼容和回滚是否遗漏。发现会改变方案的缺口时先补齐设计，再压缩表达。
7. 做保真压缩：合并重复定义，删除元话语、普通不变字段、方法清单和实现噪音；再次确认关键契约、决策、风险和边界仍完整。

只读评审与答疑不需要机械套用模板；读取目标文档和相关源码后直接给出结论、依据和必要建议。

## 架构质量要求

新建或实质修改设计时，逐项评估以下要求，将结论放入对应模块、接口、页面或上线章节。仅做措辞修改时检查是否损失原有设计信息。没有前端、外部依赖或异步流程的任务不补造对应设计；存在适用性疑问时说明判断依据。

1. **架构与领域优先**：以符合业务目标和领域规律的理想架构为目标，完整说明职责、边界、依赖和数据流后再进入编码。不得为短期实现便利牺牲整体设计。设计完整、实现克制；单一场景直接实现，第二个真实用例出现后才考虑抽象，并核对业务语义及变化方向是否一致。
2. **模块质量**：模块应高内聚、低耦合，以精简且稳定的接口封装内部复杂度。说明模块职责、命名、依赖和扩展位置，按单一职责划分。将单个代码文件不得超过 500 行列为实现约束；涉及接近上限的文件时，优先设计模块边界重构，避免仅按行数拆分。
3. **模型与状态边界**：协议模型、领域模型、持久化模型和视图模型各自维护边界。明确边界处的校验责任和独立转换，禁止跨层泄漏内部模型或共享可变状态。文档可省略普通字段传递，但必须保留这些设计责任。
4. **安全与隔离**：默认按多租户、多用户设计，明确身份来源、认证、授权、资源归属和租户隔离。遵循最小权限，外部输入均视为不可信；敏感信息不得进入代码、日志或响应。查询、缓存和异步任务也应保持隔离边界。
5. **并发与故障**：后端应评估幂等、竞态、事务、超时、取消、重试、背压和资源释放。对适用机制说明责任方、边界和失败行为；重试必须有上限或截止条件，禁止吞错、无边界重试和隐式共享状态。
6. **前端体验**：存在前端变化时，说明 UI 职责、渲染成本、异步状态和并发请求控制，覆盖加载、空状态、错误、重试、操作反馈及可访问性。明确取消或过期响应的处理，防止旧结果覆盖新状态。
7. **复用与依赖**：优先复用稳定的业务语义，不因代码外形相似提前抽象。确需重复时，将独立演进或暂不抽象的原因记录为代码注释要求。提出新增依赖前，核查项目依赖清单；Node.js 项目检查根 `package.json` 与 `packages/` workspace，并查阅已有库的文档和类型定义。记录已核实的能力缺口，再选择成熟且维护良好的库，避免重复实现通用功能。
8. **维护上下文**：非显然决策、兼容约束、已知缺陷和临时方案应记录原因、影响范围和风险；临时方案还应有移除条件。技术债务关联可追踪任务，关键架构决策同步 ADR，禁止无上下文的 TODO。没有任务编号时标记待建立任务，不编造编号；未获授权修改 ADR 时，列出目标文档和待同步决策。
9. **验证与观测**：每项变更明确可验证的行为、观测信号和故障定位方式，并评估向后兼容及回滚路径。错误和日志保留诊断上下文，同时排除敏感信息。设计中写清验证标准和观测位置即可，无须展开独立测试计划。
10. **内部清理与外部契约**：内部路径重构以移除过时实现为目标，禁止为旧内部代码新增兼容层、deprecated shim 或双写。对 `/api/*` 等稳定接口和数据库迁移，按契约单独评估兼容义务；若迁移需要过渡机制，明确适用契约、持续期限、验证方式和退出条件。记录待移除的实现和调用方迁移范围；本技能仅形成设计，不执行代码、文件或数据删除。

## 设计边界表达

- 方案摘要、数据模型、接口和关键流程默认正向说明本期采用的设计、复用关系、责任和数据流。
- 不机械复制需求文档的全部非本期范围。只有会影响数据模型、API、服务职责、兼容、发布或回滚决策的边界，才进入技术方案，并说明影响或理由。
- 权限拒绝、失败处理、扫描排除条件、兼容约束和回滚边界属于实现行为，放在对应接口、流程或上线章节，不归入泛化的“不做”清单。
- 当前方案与目标方案存在差异时，只在最自然的设计章节完整对比一次，其他章节引用该结论。

## 不可丢失的信息

- 数据模型：说明负责服务、作用、关系、相关字段、类型、约束和变化。结构不变但写入值、查询规则或状态含义变化时，也要明确写成变更。
- 数据库：存在 schema 变化时保留完整评审 DDL，并确保与数据模型章节一致；不猜测生产 Online DDL 参数，不绕过数据库变更授权。
- API：逐项明确接口、请求和返回属于新增、变更、删除或不变。新增接口列完整直接业务字段；现有接口只列变化字段和影响兼容、权限、状态或幂等的重要不变字段。
- 服务归属：每个 HTTP API 写清提供服务；每个跨服务 Facade 写清提供方和调用方。Facade 只概括新增、变更和不变内容，不重复完整内部 DTO。
- 关键实现：说明由谁负责、状态如何变化、上下游怎样协作，以及相关权限、事务、幂等、一致性和失败边界。
- 上线准备：说明 DDL、数据处理、配置、外部资源、任务、混合版本发布顺序、启用门槛和回滚边界。没有额外准备时明确说明沿用现有发布流程。

## 写作与表达

- 使用金字塔结构：章节先给结论，再展开依据、规则和例外。
- 同一层级的内容使用一级 bullet；一个列表混合多个主题时，先按主题分组，再使用二级 bullet。最多使用两级 bullet，只有一个子项时不增加父级。
- 有先后关系的操作、发布和回滚步骤使用编号列表。
- 字段、契约、配置、任务参数、实体对照和固定映射优先使用表格；结论、原因、责任、例外和失败处理使用短段落或 bullet。
- 图或表已经说清楚的内容，下文不换一种说法重复。总体说明只有在补充结论、范围或关键边界时保留。
- 同一字段、对象或业务规则只完整定义一次；其他位置说明适用范围或引用对应小节。
- 一个段落或列表项只表达一个中心意思，不用连续分号串联多个层次。
- `事务`、`幂等`、`at-least-once`、`at-most-once`、`best-effort` 等标准术语可以直接使用。`业务事实`、`成功口径`、`语义收敛`、`共用能力`、`兼容契约`、`不扩大用途` 等宽泛表达必须改成具体的数据、状态、责任或行为。
- 删除只描述写作方式、对读者没有设计价值的元话语，例如“下文只展开变化字段”。
- 简洁不等于字少。优先保留契约、决策、理由、风险和边界，再删除重复说明、调查过程、通用背景和普通不变字段。

## 数据模型与图示边界

数据模型章节讨论需要独立保存、传输或维护生命周期的业务数据结构。同步 HTTP/RPC 请求响应、方法参数、前端状态和单次请求内的临时结构放在对应接口或流程中。

对象存储路径、访问签名和生命周期只有在其存储结构本身发生变化时才作为数据模型展开；普通上传、签名和读取流程放在后端实现或上线准备中。ER 图只画实体及关联，不放对象存储、API DTO、缓存、队列、定时任务或普通处理步骤。

图示只在能明显降低理解成本时使用，最多两张：

- 跨系统调用复杂时使用自上而下的架构图；异步回调或调用回路复杂时使用时序图。
- 多个实体存在重要关系时，在数据模型章节使用简洁 ER 图，标记新增、变更、现有、负责服务、实体作用和关联字段。
- 图只表达整体关系，正文仍是字段、契约和规则的事实来源。

## 输出边界

默认输出到：

```text
docs/technical-designs/{ticket-id-or-date}-{feature-name}.md
```

遵守项目已有目录和命名习惯。输出后停止，不拆 Implementation Units，不编写测试计划，不修改业务代码。

- 需求不清楚时使用 `$requirements-clarification`。
- 方案确认后，用户要求实施计划时使用 `$implementation-plan-writing`。
- 长期模块边界、数据所有权或架构约束变化时，先在本次设计中说明决策；用户要求同步长期架构文档时，如 `$architecture-doc-writing` 可用则使用，否则按项目现有格式更新已授权的目标文档。

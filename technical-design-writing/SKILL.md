# Technical Design 编写

## 目标

为单个具体软件需求编写一份熟悉项目的人能顺着调用链阅读、讨论并作出决策的技术设计。

Technical Design 回答：

- 需求涉及哪些数据模型，当前模型和目标模型分别是什么？
- 每个业务流程从哪里进入，经过哪些具体应用、模块和关键方法？
- 输入输出怎样变化，各应用和模块分别承担什么核心修改？
- 正式上线前需要准备什么，按什么依赖顺序发布、启用和回滚？
- 哪些兼容性、权限、一致性或发布问题需要评审？

它是设计评审材料，不是 Coding Agent 的实施任务书。默认状态为 `Draft`；只有用户或项目流程明确确认后，才标记为 `Approved`。

## 输入与事实来源

按问题类型使用对应来源：

- 当前用户指令和需求决定目标、范围和业务语义。
- `AGENTS.md` / `CLAUDE.md` 决定项目规则和允许的操作。
- 用户指定的参考文档决定期望的文档结构和表达方式；必须完整阅读。
- 用户未指定参考文档时，检查目标目录中的同类方案，并至少读取一份有代表性的现有文档。项目已有写法优先于通用模板。
- 当前源码、配置、schema 和测试决定系统现在怎样；与说明文档冲突时，以源码为准并指出文档漂移。
- 架构文档和 ADR 决定长期边界和约束。
- 外部官方文档只用于确认依赖、协议或平台 contract。

不要把需求文档中的设想写成“当前实现”，也不要用未经源码验证的类名、方法名或流程细节。

同时提供需求、现状、技术方案和实施计划等多个文档时，先区分目标文档和只读参考。用户只要求“核对”“评审”或明确“先别改”时，不修改任何文件；用户要求更新时，只修改明确指定的目标文档，不把参考文档当作修改对象。

## 工作流程

1. 读取项目规则、需求、现状说明、架构文档和用户指定的参考方案；没有指定参考时读取一份项目内同类方案。
2. 整理目标、范围、Non-Goals 和待确认事项。关键业务语义不清楚时，先转 `$requirements-clarification`；可安全推断的信息标记为 `假设：`。
3. 按具体应用盘点受影响入口，建立受影响 API 清单，只纳入直接修改或虽不修改但构成重要兼容边界的接口，逐项确认接口本身、请求、返回和关键业务语义属于新增、变更、删除或不变。该清单用于防止遗漏，不要求原样搬入成稿。根据源码确认页面或组件入口、HTTP、Controller、触发方法、主要调用关系、输入输出和数据访问，并核实变化字段的名称、类型、定义、默认值和兼容规则。分析可以追到实现底层，最终文档只保留职责发生变化的入口、Controller、关键方法和应用间调用关系；不展示未变化的中间调用过程。
4. 对每个新增或职责变化的接口、数据访问、事件消费或定时任务，在同一应用和同类能力中选择一处最接近的现有实现作为参考，核对模块分层、命名、契约组织、校验与鉴权、错误返回、事务和持久化方式。优先沿用现有模式；现有做法与需求或架构约束冲突时采用最小必要偏离，并把需要评审的理由写入方案。参考代码用于约束设计，不在成稿中罗列调查过程。
5. 单独盘点数据模型：关系型或文档数据库、搜索索引、缓存、消息队列或事件、持久化异步任务和对象存储。区分结构变化与写入、查询、取值或生命周期语义变化，只纳入直接修改或虽不修改但构成重要兼容边界的模型，并核实相关结构、字段、类型和约束。
6. 设计满足需求的最小方案，保留现有数据所有权和应用边界。前端只说明页面、交互、状态和请求参数；后端按接口能力或后端业务流程说明契约与实现，ES、DB、缓存、消息等放在对应后端实现中概括。
7. 单独盘点上线前准备：数据库脚本与数据迁移、配置中心与外部资源、需要管理平台创建或启用的定时/异步能力、混合版本兼容顺序、产生新数据的入口、启用门槛和回滚边界。逐项核对所属应用、现有项目习惯和环境差异；不能确认的生产值不得伪造。
8. 读取 `references/technical-design-template.md` 并起草。完成后做一次编辑整理：合并相似接口，删除重复规则和方法清单，拆开同时表达多个意思的长句，确认只看标题也能理解方案顺序。
9. 更新既有 Technical Design 时，先全局搜索受影响的接口、模型、枚举、上线事项和结论，在原有责任章节修改并删除失效表述；完成后重新检查摘要、架构图、接口表、上线前准备和注意事项，不追加独立的补充说明。
10. Review 时读取 `references/technical-design-review-checklist.md`，修正后输出。
11. 输出后停止，不拆 Implementation Units，不编写测试计划，不修改业务代码。用户继续要求实施计划时，转 `$implementation-plan-writing`。

## 文档组织原则

正文固定按读者的查阅路径组织：

1. 用短摘要说明方案结论和边界。
2. 跨系统或调用关系复杂时，用一张简洁图说明整体关系。
3. 单独写“数据模型变更”。本节必填；没有变化时明确写“无”，并说明继续使用哪些现有模型。
4. 有前端改动时，单独写“前端页面改动”，按具体前端应用和页面或功能组织。
5. 单独写“后端接口和实现变更”，按接口能力或后端业务流程组织。
6. 单独写“上线前准备”。本节必填；没有额外准备时明确写“无”，并说明沿用现有发布流程。
7. 最后只保留有决策价值的其他注意事项、主要影响范围、待确认事项和依据。

前端和后端必须分章，不在同一个小节里同时罗列页面方法、HTTP、Controller 和数据查询。完整调用关系由架构图或章节开头的一两句话连接，不靠混写各层细节表达。ES、DB、缓存和消息不是主章节，它们是对应后端接口或后端流程的实现细节。

写到能支持设计评审为止：

- 前端页面改动先用一句话说明用户可见变化，再写具体应用、页面或组件入口、关键交互和状态、提交给后端的请求参数。前端章节不写 Controller、后端 DTO、ES、DB、缓存和消息处理，也不穷举组件、Hook 和事件处理方法。
- 后端 HTTP 接口先用一句话说明接口责任和结果变化，再写具体应用和模块、HTTP、Controller、职责发生变化的核心入口、输入输出变化和核心修改。后端章节不枚举前端组件和页面方法。多个用途相近且契约一致的接口可以合并，用表格列出入口。
- 后端非 HTTP 流程先写结果，再写具体应用和模块、触发入口、关键方法、输入输出或状态变化，以及核心修改。
- 每个受影响接口先分别说明接口、请求和返回属于 `新增`、`变更`、`删除` 或 `不变`。字段级只展开新增、变更、删除字段，以及会影响兼容性、权限、状态、幂等或业务边界的重要不变字段；其余用“其他字段不变”合并说明。
- 新增接口列出实现所需的完整直接业务请求和返回结构。现有接口按增量说明，不复制完整 DTO、公共响应外壳、继承字段和与本需求无关的字段。
- 请求或返回结构不变，但过滤、排序、统计口径、允许值、默认值或副作用变化时，明确写成“结构不变，语义变更”。
- 请求字段属于对应接口契约。不要为请求字段、内部 DTO、转换参数或查询参数单独创建“数据模型”或“内部模型”章节。多个接口共享字段时，在同一个接口能力小节中定义一次，并明确适用的接口。
- 核心修改说明“改什么、由哪个后端应用或模块负责、如何与上下游协作”。ES 查询、DB 回退、缓存读写、事件发布或消费等内容放在对应后端接口或流程中，只说明影响方案判断的关键语义和责任。
- 核心修改通常合计 2—4 条。每条只表达一个重点；能删除且不影响方案判断的技术细节、业务示例和重复规则应删除。只有缺少细节会造成方案语义不明确时，才补充必要说明。
- 列主要影响模块和关键文件即可，不写机械文件清单。
- 只解释真正存在选择空间、风险或反直觉的决策。
- 不添加“验收重点”或 `Planning Handoff` 章节。

使用源码中的具体应用、模块、接口和方法名称，例如 `coc-ohappcore`、`OrgMngController#list`。最终文档不得用角色简称代替具体责任方；即使参考材料使用角色简称，也要还原为实际应用、模块和职责。只有方案确实需要新增公共抽象时才命名新概念，并说明它解决的问题。

## 写作与可读性

- 区分“契约精确”和“实现概要”：接口与数据模型的字段名称、类型、定义和默认值必须准确；内部实现只说明行为规则、责任边界和必须保持的一致性，不把源码调查结果逐层搬进正文。
- 区分“重要不变”和“普通不变”。旧调用方兼容、接口继续保留、无需修改表结构、关键字段仍为空或某项能力明确不支持等属于重要不变；通用 ID、时间戳、公共响应字段和无关 DTO 字段通常合并说明。
- 变更总览用于防漏，不替代详细说明。受影响对象较少时直接在对应小节给出结论；对象较多时才使用总览表。
- 不为证明“完整”而复制完整 Schema、DTO 或响应对象。文档完整性来自变化结论无遗漏，而不是字段数量多。
- 没有删除项时，在相关总览或章节开头用一句话统一说明，不在每个小节重复。
- 每个主章节和小节先用一两句话给出结论，再提供入口、字段和实现依据。不要让读者从方法清单中自行归纳结论。
- 标题直接使用具体应用、页面、接口能力或业务流程名称。连续阅读标题时，应能看出“数据是什么、前端改什么、后端怎样实现”。
- 表格用于接口入口映射、字段和数据结构等重复且需要精确对齐的信息；正文用于说明方案结论、责任和理由。不要把所有内容都拆成列表。
- 同一业务规则只完整说明一次。其他接口需要复用时，指出适用范围或引用所在小节，不换一种说法重复解释。
- 一个段落或列表项只表达一个中心意思。拆开包含多个转折、条件和实现层次的长句，避免连续使用分号。
- 每个前端应用只列一个主要页面或组件入口，复用页面只概括影响范围；每个后端应用只列一个主要 Controller 或核心方法。内部 DTO 的传递链、条件构造步骤和数据访问参数由实现阶段根据源码完成，除非它们本身构成需要评审的契约或设计选择。
- 使用项目中的普通名称，不引入 `BFF`、`Facade 层` 等读者需要额外解释的角色术语。若源码类型本身名为 `Facade`，可以写实际类型名，但责任说明仍使用具体应用和模块。

## 数据模型边界

“数据模型”是具有独立存储、传输或生命周期的数据结构，不限于数据库表，包括：

- 关系型数据库、文档数据库及其字段、关系、约束和状态；
- ES 等搜索索引的文档结构、字段和 Mapping；
- 缓存的 key、value、TTL、失效与一致性语义；
- 消息队列、领域事件和持久化异步任务的 topic、payload、业务键、顺序与幂等语义；
- 对象存储的路径、元数据、生命周期和访问方式；

同步 HTTP / RPC 请求响应、方法参数、前端组件状态和单次请求内的临时结构不属于本节数据模型。它们的变化放在对应业务流程的“输入输出修改”或“核心修改”中；即使为了说明“不持久化”，也不在数据模型章节中提及。

对直接变化的数据模型说明当前模型、目标变化、所有权、稳定标识、生命周期和兼容方式。结构不变但写入值、查询规则或状态语义变化时，模型总体标记为“变更”，并明确说明不涉及结构或 DDL 变化。

完全不变的数据模型只有在构成重要兼容边界或容易被误改时才写入，用一句话说明继续复用以及无需修改的原因，不为其逐项列出不变字段。

数据模型章节必须给出支持方案判断的相关结构和字段：

- 数据库表说明所属应用、表用途，以及相关字段的名称、物理类型、可空性或键约束、定义和变化；
- ES 等搜索索引说明所属应用、索引或文档模型，以及相关字段的 Mapping 类型或代码模型类型、结构和定义；
- 缓存说明所属应用、key 格式、value 类型或结构、TTL、失效方式和用途；
- 消息或事件说明生产与消费应用、topic 或事件名称、业务键，以及 payload 字段的类型和定义；
- 持久化任务和对象存储按同样原则说明关键结构、类型、生命周期和归属。

只列本需求相关字段，不复制完整 Schema。物理类型必须来自 DDL、Mapping 或正式契约；只有代码模型证据时标记为逻辑类型，不能推测物理类型。无法确认的类型明确写“仓库未确认”并说明已有证据。

## 接口契约说明

每个受影响的接口、事件或回调都分别说明接口、请求和返回属于新增、变更、删除或不变；过滤、排序、状态、统计口径、权限或副作用变化时，再补充关键语义。新增契约列出完整的直接业务字段。现有契约只列新增、变更、删除字段和重要不变边界，其他字段合并说明为“不变”。“不变”不能只通过省略表达，也不需要逐字段证明。

展开字段时优先使用紧凑字段表，至少包含字段、类型、是否必填、定义与默认值、变化。类型使用对外契约中的实际表达；集合写明元素类型，对象引用具体结构。若代码类型与线上 JSON、RPC 或消息类型不同，同时说明两者。

## 上线前准备边界

“上线前准备”固定保留，只写普通代码部署之外必须完成的环境准备，以及为保证混合版本兼容而必须明确的发布、启用和回滚顺序。目标数据结构和运行时行为仍由前面章节定义，本节只说明如何安全地把它们准备并投入使用，不重复整套设计。

- 数据库与数据：说明版本化 DDL 或迁移脚本的所属应用、旧数据处理、是否回填和执行前核对事项。需要展示 DDL 时必须与数据模型章节一致，并参考项目现有 DDL 习惯；将 SQL 标明为评审稿或迁移内容，不猜测生产 Online DDL 参数，也不绕过数据库变更授权。
- 配置与外部资源：说明配置键、所属应用、用途、结构、默认值、缺失行为，以及通知场景、静态资源、白名单或环境权限等外部准备。示例值和占位符必须明确，不能伪造生产场景 ID、域名、账号或密钥。
- 定时与异步能力：说明需要在管理平台创建或调整的任务、订阅或开关，包括所属应用、Handler 或 Topic、Cron 或触发方式、时区、参数、初始状态和启用门槛。代码存在不等于允许立即启用。
- 发布与回滚：只写跨应用、跨版本和端侧兼容所要求的依赖顺序，例如“公共契约 → 数据结构 → 兼容 Provider → Consumer 与读取能力 → 产生新数据的入口 → 延后启用任务”。说明怎样停止新增写入或异步触发，并保留已产生数据所需的读取能力；不使用删除字段或数据作为默认回滚方式。
- 权限、安全、一致性等运行时设计继续放在相关业务流程或“其他需要注意的地方”。只有需要上线人员实际准备的环境权限、白名单或开关才放在本节。

不默认添加上线监控检查。需求、架构约束或用户明确要求监控时，只说明影响方案评审的监控边界，不扩展为运维验收清单。没有数据库、配置、资源、任务或特殊发布顺序时，用一句话明确“无额外上线前准备，沿用现有发布流程”，并删除空小节。

## 图示规则

图示只在能明显降低理解成本时使用，最多两张。

- 架构图顶层使用 `flowchart TB`，按实际调用方向自上而下排布；同层节点可以在子图内使用 `direction LR`，不能把整张图改为横向。
- 默认层级为“调用方或前端应用 → HTTP 接入与编排应用 → 业务或通知服务 → 数据存储与外部系统”。不看连线也应能从上下位置辨认层级。
- 每个节点使用“具体应用 + 一个关键模块、类、接口或数据存储 + 主要职责”的格式，例如 `coc-sfbizcore<br/>PatientSearchEsServiceImpl<br/>查询患者索引`。数据库、索引、缓存、消息和外部系统节点同样标明负责或接入它们的应用。
- 同一应用在同一层默认合并为一个节点；只有承担不同调用位置、数据所有权或独立流程时才拆分。不能只写应用名，也不要按每个 Controller、Service 或 Mapper 分别拆节点。
- 架构图只保留主要职责和调用方向；不能为没有对应源码模块、类或存储的处理步骤虚构节点，处理说明写在具体节点或连线上。
- 回调、异步交互或调用回路导致上下方向不清楚时改用时序图，可以标记关键 HTTP、Controller 或核心服务；不要强行把复杂时序塞进架构图，也不要展开普通内部方法和 DTO 字段。
- 图要对应后续业务流程，不能创造正文没有定义的抽象层，也不能替代入口、输入输出和修改说明。
- 正文是事实来源；图与正文不一致时，修改图，不让读者自行猜测。

简单 CRUD、字段校验、单 Service 内部修改通常不画图。

## 决策边界

Technical Design 必须明确：

- 需求已经定义的用户可见行为和范围边界；只能复述并保持，不能擅自改变。产品语义不清时转 `$requirements-clarification`。
- 数据所有权、数据库、缓存、搜索索引、消息事件、对象存储等相关数据模型和状态语义。
- API / Event contract 与跨服务责任。
- 权限、安全、事务、一致性、幂等和兼容策略中与本需求相关的部分。
- 数据库迁移、环境配置、外部资源、管理平台任务、兼容发布顺序、启用门槛和回滚边界中与本需求相关的部分。
- 需要评审的方案取舍及理由。

Technical Design 不决定：

- 需求未授权的新用户行为、产品范围或验收标准。
- 普通代码 wiring、局部变量和可由仓库约定推导的 boilerplate。
- Implementation Unit 的拆分和编码顺序。
- 验收清单、测试计划、完整文件清单、生产执行命令和提交安排。用于结构评审的 DDL、配置格式和任务触发规则不属于实施命令，但不得冒充已经确认的生产值。
- 与当前需求无关的重构和未来扩展。

## 输出位置

默认放在：

```text
docs/technical-designs/{ticket-id-or-date}-{feature-name}.md
```

如果项目已有方案目录，遵守现有目录。文件名使用小写 kebab-case；有 ticket id 时优先使用 ticket id。

## 与其他 Skill 的关系

- 需求关键语义、范围或验收标准仍不清楚时，使用 `$requirements-clarification`。
- 本技能输出并确认目标方案后，使用 `$implementation-plan-writing` 生成 Coding Agent 可执行的计划。
- 长期模块边界、数据所有权、事务或安全约束变化时，使用 `$architecture-doc-writing` 更新架构文档或 ADR。

输出后停止，不继续生成实施计划或修改代码，除非用户明确要求。

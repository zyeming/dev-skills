# Technical Design Review Checklist

先检查设计信息是否完整，再检查表达是否简洁。不能为了缩短文档删除契约、决策、风险和边界。

## 完整性检查

### 事实与范围

- [ ] 目标、本期技术变化、关键复用和必要设计边界来自已确认需求。
- [ ] 没有机械复制需求文档的全部非本期范围；保留的每项设计边界都会影响数据模型、API、服务职责、兼容、发布或回滚决策。
- [ ] 权限拒绝、失败处理、扫描排除条件、兼容约束和回滚边界位于对应接口、流程或上线章节，没有混入泛化的“不做”清单。
- [ ] 当前方案与目标方案的差异只完整说明一次，其他章节没有重复对比。
- [ ] 当前行为已根据源码、配置、DDL 或测试核实；假设没有写成事实。
- [ ] 使用实际应用、模块、接口和方法名称，没有用自造角色替代责任方。
- [ ] 修改范围只包含用户指定的目标文档，没有误改只读参考。

### 数据模型与 DDL

- [ ] 数据模型章节存在，并覆盖所有直接变化或影响旧数据兼容的模型。
- [ ] 每个模型写清负责服务、作用、关系、相关字段、类型、约束和变化。
- [ ] 字段类型来自 DDL、Mapping、正式契约或代码证据；无法确认的内容已明确标记。
- [ ] 结构不变但写入值、查询规则、状态或生命周期变化时，已明确说明。
- [ ] 数据库 schema 变化包含完整评审 DDL，且与数据模型字段、索引和默认值一致。
- [ ] 旧数据是否回填、默认值和新旧版本兼容方式清楚。

### API、Facade 与流程

- [ ] 所有受影响 API 都写明提供服务、方法和路径、接口变化、请求变化和返回变化。
- [ ] 新增 API 列出完整直接业务字段；现有 API 只展开变化字段和重要不变字段。
- [ ] 字段写明实际契约类型、必填条件、定义、允许值、默认值和兼容规则。
- [ ] 结构不变但权限、过滤、排序、统计、状态或副作用变化时，已写成语义变更。
- [ ] 每个跨服务 Facade 写清提供方和调用方，只概括必要的新增、变更和不变内容。
- [ ] 权限、事务、幂等、一致性、重试和失败处理位于相关 API 或流程中。
- [ ] 定时或异步流程写清所属服务、触发规则、扫描范围、并发语义和失败边界。

### 上线与回滚

- [ ] 上线前准备覆盖相关 DDL、数据处理、配置、外部资源、任务和启用门槛。
- [ ] 发布顺序只包含真实依赖，并保证读取兼容能力先于产生新数据的入口。
- [ ] 配置和示例没有伪造生产场景 ID、域名、账号或密钥。
- [ ] 回滚能够停止新增写入和异步触发，同时保留已产生数据所需的读取能力。
- [ ] `其他实现注意点` 只保留跨接口或跨流程规则，没有重复前文内容。

## 可读性检查

- [ ] 章节和小节先给结论，再展开依据、规则和例外。
- [ ] 同一层级使用一级 bullet；混合多个主题时使用不超过两级的分组 bullet。
- [ ] 有先后关系的操作、发布和回滚步骤使用编号列表。
- [ ] 字段、契约、配置、任务和固定映射使用表格；结论、原因和异常使用正文或 bullet。
- [ ] 图或表已经说明的内容没有在下文重复。
- [ ] 同一字段、共享对象或业务规则只完整定义一次。
- [ ] 一个段落或列表项只表达一个中心意思，没有用长句或连续分号混合多个层次。
- [ ] 宽泛概念已替换为具体的数据、状态、责任或行为；标准技术术语没有被多余解释。
- [ ] 文档没有“下文只展开变化字段”等写作元话语，也没有源码调查流水账。
- [ ] 没有机械复制完整 DTO、Schema、普通不变字段、内部参数传递链或方法清单。
- [ ] 总体说明确实补充了结论、范围或关键边界，而不是复述后面的图表。
- [ ] 删除和合并内容后，API、DDL、服务归属、决策、风险、兼容和回滚边界仍然完整。
- [ ] 熟悉项目的评审者能够快速说清整体方案、关键数据、主要接口和各服务责任。

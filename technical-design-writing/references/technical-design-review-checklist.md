# Technical Design Review Checklist

检查重点是文档能否用项目已有名称，简洁讲清实现重点，使熟悉项目的人能够快速理解和评审方案。

## 事实与范围

- [ ] 目标、范围和明确不做的内容清楚。
- [ ] 当前行为已根据源码核验；文档漂移已指出。
- [ ] 目标行为完整满足需求，没有提前实现未来能力。
- [ ] 用户可见行为和范围来自需求；设计没有擅自增加或改写产品语义。
- [ ] 假设和待确认事项没有被写成事实。

## 数据模型

- [ ] “数据模型变更”章节始终存在；没有变化时只用一个短段落说明相关模型和无需修改的原因。
- [ ] 已识别需求涉及的数据库、搜索索引、缓存、消息或事件、持久化任务和对象存储模型。
- [ ] 相关数据模型写明所属应用、结构、字段名称、可验证的类型、约束和业务定义。
- [ ] 数据库、索引、缓存、消息等模型的所有权、关键关系或状态、一致性和兼容方式足以支持方案判断。
- [ ] 字段类型来自 DDL、Mapping、正式契约或代码模型；证据不足时已明确标记，没有自行推测。
- [ ] 数据模型章节只讨论数据模型；同步请求响应、方法参数和单次请求内的临时结构只出现在对应业务流程，没有以“不持久化”为由写入本节。
- [ ] 每个直接变化或构成重要兼容边界的数据模型都有新增、变更、删除或不变的明确结论。
- [ ] 已区分结构变化与写入、查询、取值、状态或生命周期等语义变化；结构不变时没有误写成需要 DDL。
- [ ] 完全不变的模型只在影响方案判断时保留，没有逐项罗列普通不变字段。

## 前端与后端实现

- [ ] 前端页面改动与后端接口实现分章说明，没有在同一小节混写组件方法、HTTP、Controller 和数据查询。
- [ ] 前端章节按具体前端应用和页面或功能组织，先说明用户可见变化，再简要说明页面入口、关键交互与状态、请求参数。
- [ ] 每个前端应用只保留一个主要页面或组件入口，复用范围已概括，没有把组件和方法清单搬入正文。
- [ ] 前端章节没有展开 Controller、后端 DTO、ES、DB、缓存和消息处理。
- [ ] 后端章节按接口能力或后端业务流程组织，先说明结果变化，再写具体应用、HTTP、Controller、变化的输入输出和核心修改。
- [ ] 后端章节没有枚举前端组件和页面方法；ES、DB、缓存和消息处理位于对应后端接口或流程中。
- [ ] 正文直接使用实际应用和模块名称；即使参考材料使用角色简称，也已还原为具体责任方。
- [ ] 每个接口或流程突出“改什么、由谁负责、如何协作”，内部实现停留在行为规则、责任边界和一致性要求的概要层面。
- [ ] 用途相近且契约一致的接口已合并说明；每个应用只保留最关键的入口或方法。
- [ ] 正文没有展示不影响方案判断的中间调用过程、技术细节、业务示例或重复规则。
- [ ] 每个新增或职责变化的接口、数据访问、事件消费和定时任务都核对了同一应用中的同类实现。
- [ ] 新设计沿用了现有模块分层、命名、契约组织、校验与鉴权、错误返回、事务和持久化方式；必要偏离已有明确理由。
- [ ] 每个受影响 API 的接口、请求和返回都有新增、变更、删除或不变的明确结论，没有通过省略表达“不变”。
- [ ] 已区分请求或返回结构变化与过滤、排序、统计口径、允许值、状态或副作用等语义变化。
- [ ] 新增契约包含实现所需的完整直接业务字段；现有契约只展开新增、变更、删除字段和重要不变边界。
- [ ] 展开的接口字段写明类型、是否必填、业务定义、允许值、默认值和兼容方式；集合和对象结构清楚，未展开字段已有合并的不变结论。
- [ ] 契约字段足够精确，但没有为了显得具体而展开内部参数传递链和条件构造过程。
- [ ] 请求字段位于对应接口的输入输出说明中，没有被写成独立的数据模型、公共请求语义或内部模型章节。
- [ ] 权限、安全、事务、一致性、幂等和运行时兼容只在相关时展开；上线动作集中到“上线前准备”。
- [ ] “其他需要注意的地方”只保留跨流程关注点，没有重复各流程已经说明的实现。
- [ ] 真正存在选择空间的决策写清选择和理由。
- [ ] 关键风险有对应的缓解或待决策动作。

## 上线前准备

- [ ] “上线前准备”章节始终存在；没有额外准备时已明确写明沿用现有发布流程，没有保留空小节。
- [ ] 已盘点数据库与数据迁移、配置与外部资源、管理平台任务或异步能力、兼容发布顺序、启用门槛和回滚边界，仅保留与本需求有关的事项。
- [ ] DDL 或迁移内容与数据模型章节一致，并符合项目现有表结构和 DDL 习惯；脚本所属应用、旧数据处理、生产核对事项和数据库变更授权边界清楚。
- [ ] 没有猜测生产 Online DDL 参数；评审 SQL、版本化迁移内容和实际生产执行边界已经区分。
- [ ] 配置和外部资源写明所属应用、用途、结构或取值、默认值和缺失行为；示例或占位符没有冒充实际场景 ID、域名、账号或密钥。
- [ ] 定时任务、订阅或开关写明所属应用、Handler 或 Topic、Cron 或触发规则、时区、参数、初始状态和启用条件。
- [ ] 发布顺序只包含保障混合版本兼容所需的依赖，读取能力先于产生新数据的入口，延后启用的任务有明确门槛。
- [ ] 回滚能够停止新增写入或异步触发，同时保留已产生数据所需的读取能力；没有默认删除字段、结构或数据。
- [ ] 上线前准备没有重复第 1～3 章的完整设计，也没有出现 Implementation Units、测试场景、生产执行命令、提交安排或默认监控清单。

## 架构与图示

- [ ] 方案没有破坏既有模块边界、数据所有权和架构约束，或明确说明例外。
- [ ] 需要图时使用简洁架构图或时序图，主要调用方向清楚，并与后续业务流程对应。
- [ ] 架构图整体自上而下分层，同层节点才横向排列；不看连线也能辨认调用方、接入编排、业务服务和存储层级。
- [ ] 同一应用没有被按普通内部类过度拆分，也没有被合并成只剩应用名、看不出关键入口和职责的节点。
- [ ] 图中的每个节点都标明具体应用，并写清对应模块、类、接口或数据存储。
- [ ] 数据库、索引、缓存、消息和外部系统节点同样标明负责或接入它们的应用。
- [ ] 图中没有为缺少源码对应物的处理步骤虚构节点；必要说明位于具体节点或连线上。
- [ ] 图与正文一致，图没有重复正文或充当装饰。

## 可读性与边界

- [ ] 摘要、主章节和小节都先给结论，不要求读者从入口和方法清单中自行归纳方案。
- [ ] 标题按“数据模型 → 前端页面 → 后端接口和实现 → 上线前准备”形成清楚的阅读顺序；没有前端改动时已删除空章节并顺延编号。
- [ ] 表格只用于需要精确对齐的接口、字段和数据结构；正文用于说明结论、责任和理由，没有把所有内容都拆成列表。
- [ ] 同一业务规则只完整说明一次，其他接口通过适用范围或引用建立联系。
- [ ] 每个段落或列表项只表达一个中心意思，没有用长句和连续分号混合多个层次。
- [ ] 更新既有方案时已全局检查相关名称和结论，没有残留失效表述、重复规则或前后矛盾。
- [ ] 文档没有“验收重点”或 `Planning Handoff` 章节。
- [ ] 没有 Implementation Units、逐步编码任务、机械文件清单或精确测试命令。
- [ ] 文档保留了实现所需的关键信息，没有把源码分析过程、完整接口文档或详细设计整体搬入正文。
- [ ] 重要不变边界已明确，普通不变字段已合并，没有机械复制完整 DTO、Schema 或响应对象。
- [ ] 只使用必要且已经定义的概念；新增概念确有设计价值并说明了用途。
- [ ] 没有用 `BFF` 等自造角色词替代具体应用和模块；源码中的 `Facade` 类型仅作为真实名称出现。
- [ ] “依据”只保留支持关键判断的来源，不写阅读流水账。
- [ ] 一名熟悉项目的评审者能快速说清整体方案、主要入口、输入输出变化和各模块职责。

# 架构文档编写

## 目标

使用本技能编写对人类开发者和 AI Coding agent 都有用的架构文档。

架构文档是设计约束文档，不是代码导览、API 手册或实现百科。默认写收敛版文档：记录稳定、非显而易见、违反代价高的规则，帮助未来开发回答：

- 系统或模块拥有什么责任？
- 系统或模块明确不负责什么？
- 哪些边界不能跨越？
- 哪些不变量、状态流转、事务、事件、幂等和安全规则必须保留？
- 新功能应该怎样安全加入？
- 哪些看似方便的捷径是禁止的？

## 核心规则

只写同时满足以下两道门槛的信息。

第一道：它必须保护至少一种架构风险：

- 模块边界、依赖方向或所有权。
- 状态事实来源、状态机或业务不变量。
- 数据一致性、事务边界、幂等、并发或失败收敛。
- 安全、权限、租户隔离或敏感数据处理。
- 外部系统适配、事件语义、后台任务或回调约束。
- 常见扩展路径中容易被误改的规则。

第二道：它不能由其他材料更合适地承载：

- 代码、类型、测试或 schema 已经清楚表达，且误改代价不高的，不写。
- Swagger、API 文档、README、前端 guide 更适合承载的，不重复写。
- 只是“当前有哪些类、函数、字段、文件”的，不写。

不要写：

- 每个文件、类、函数、接口字段、数据库字段或 API 参数。
- 完整 API contract、完整事件 payload、完整目录树。
- 服务、组件、事件、接口的百科式清单。
- 普通调用链、普通 CRUD 流程、框架显而易见的默认行为。
- 临时实现细节、调试记录、生成文档。
- 未经确认的猜测。

事实与命名必须满足以下要求：

- 以当前代码、schema、配置和测试能够验证的行为为准，不把目标设计或历史印象写成当前事实。
- 使用源码中的真实模块名、类名、DO 名、物理表名、状态名和关联字段，不为易读性创造代码中不存在的实体或别名。
- 先解释实体是什么、保存什么核心信息，再说明实体关系、状态变化和业务流程。
- 图中的节点和连线优先使用真实名称与真实关联字段；需要补充业务含义时，将说明附在真实名称之后，不用说明替代真实名称。
- 无法从当前材料证明的结论标记为 `假设：` 或 `未决问题：`，不得写成确定事实。

判断规则：

```text
如果违反这条信息会造成隐藏耦合、数据不一致、安全问题、权限绕过、难以回滚的设计漂移，写进文档。

如果这条信息只是帮助读代码更快，但不保护架构约束，删掉或改成引用。
```

## 工作流程

1. 先读现有约束：
   - `CLAUDE.md`
   - `AGENTS.md`
   - 现有 `ARCHITECTURE.md`
   - 现有模块架构文档
   - 现有 ADR
   - 用户给出的项目规则

2. 再观察代码中的架构信号：
   - 目录和模块结构中体现的责任边界，不是完整文件树
   - public entry points 中体现的权限、幂等、事务和状态写入边界
   - 依赖方向和禁止跨越的内部实现
   - 数据模型背后的数据所有权和事实来源
   - 事务和一致性边界
   - 事件、队列、后台任务、回调和外部集成中的所有权、顺序、幂等和失败收敛
   - 认证、授权、租户隔离和安全检查
   - 测试中体现的不变量和公开契约，不搬运测试细节

3. 写作前先分类候选信息：
   - `必须写`：不写会导致未来修改破坏边界、所有权、不变量、事务、安全或一致性。
   - `一句带过`：有上下文价值，但不是核心约束。
   - `引用已有文档`：已有 README、API 文档、前端 guide、ADR 或测试更适合承载。
   - `不写`：代码已经清楚表达，或没有架构后果。

4. 选择文档类型：
   - 项目级规则写根级 `ARCHITECTURE.md`。
   - 单个模块、服务、bounded context 写模块级 `ARCHITECTURE.md`。
   - 重要决策、边界变化、取舍和例外写 ADR。

5. 只在需要时读取对应模板。模板是候选材料清单，不是必填章节：
   - 根级架构文档：`references/root-architecture-template.md`
   - 模块架构文档：`references/module-architecture-template.md`
   - ADR：`references/adr-template.md`

6. 编写时优先使用约束句式：
   - `规则：`
   - `原因：`
   - `允许：`
   - `禁止：`
   - `例外：`

7. 对不确定信息明确标记：
   - 用 `假设：` 标记从代码结构推断但未确认的信息。
   - 用 `未决问题：` 标记需要维护者决策的问题。
   - 不要把猜测写成事实。

8. 自检并收敛：
   - 删除空泛章节。
   - 删除只重复代码的内容。
   - 删除与当前代码不一致的理想化描述。
   - 删除只说明“有什么文件/接口/事件”的清单。
   - 检查文档中的模块、类、DO、表、字段和状态名称能否在当前材料中定位。
   - 检查图中的节点、关联方向和关联字段是否与正文及代码证据一致。
   - 检查引用链接、Markdown 围栏和 Mermaid 结构是否有效。
   - 确认所有保留内容都在保护真实边界、所有权、不变量、事务、安全或扩展规则。

## 文档选择规则

根级 `ARCHITECTURE.md` 的候选内容：

- 项目目的和非目标。
- 系统级原则。
- 模块边界和依赖方向。
- 数据所有权。
- 事务、一致性、事件和后台任务策略。
- 安全、授权、观测性规则。
- AI Coding contract。

只保留系统级、跨模块、违反代价高的规则。已有模块文档能说明的内容，在根文档中引用，不重复。

模块级 `ARCHITECTURE.md` 的候选内容：

- 模块责任和非责任。
- 对外稳定入口及其权限、状态、事务或幂等边界。
- 内部结构中的所有权和依赖规则。
- 核心概念、不变量、状态机。
- 事务边界、幂等、事件语义、外部依赖约束。
- 持久化、安全和常见变更方式。

只保留有架构风险的内容。完整 API、事件 payload、字段说明和普通开发步骤应留给代码、类型、Swagger、README 或专门 guide。

使用 ADR 记录：

- 模块边界变化。
- 数据所有权变化。
- 事务或一致性模型变化。
- 新事件驱动流程。
- 重大依赖引入。
- 安全敏感决策。
- 接受有代价的捷径。
- 故意违反既有架构规则的例外。

## 与技术实现方案的边界

本技能不用于编写单个需求的 Technical Design / Implementation Plan。

如果用户要的是“这次需求怎么实现、改哪些模块、风险和测试是什么”，应使用 `$technical-design-writing`。

架构文档记录长期稳定约束；技术实现方案记录具体需求的短中期实现蓝图。若技术方案改变了长期约束，再回到本技能更新 `ARCHITECTURE.md`、模块架构文档或 ADR。

## 写作规则

默认使用中文编写文档。代码标识符、文件路径、类名、函数名、命令、事件名和配置名保持原文。

优先写所有权和约束：

- `X 是 Y 状态的唯一写入口。`
- `X 的输出只是 proposal，只有 Y commit 后才是事实。`
- `X 只能通过 Y 调用 Z，不得直接访问 Z 的内部实现。`
- `重复请求必须复用同一 idempotency key，不得产生第二次副作用。`

使用明确、规范性的表达：

```md
规则：
Payment 模块不得直接修改 Order 状态。

原因：
Order 状态流转必须经过 Order 模块的状态机校验，否则会绕过业务不变量和审计逻辑。

允许：
Payment 模块可以发布支付完成事件，或调用 Order 模块公开的应用服务。

禁止：
Payment 模块不得直接写入 orders 表或调用 Order 内部 repository。
```

避免模糊表达：

```md
Payment 和 Order 有关系。
通常 Payment 可以更新订单状态。
```

如果主规则在代码里存在例外，必须写清楚：

```md
例外：
AdminRepairJob 可以直接修复 Order 状态，但只能处理历史脏数据，且必须记录审计日志。业务流程不得复用该入口。
```

## 假设和未知

不要编造架构事实。

如果代码结构暗示某条规则但不能证明，写：

```md
假设：
当前目录结构显示 payment 模块拥有支付状态。若后续要移动支付状态所有权，需要先与维护者确认并补充 ADR。
```

如果问题尚未决策，写：

```md
未决问题：
报表查询是否允许直接读取业务表，还是应该引入专用 read model？
```

## 质量检查

交付前用这些问题裁剪内容。只有当问题对应真实架构风险时才回答，不要为了覆盖清单而写：

- 系统或模块拥有什么？
- 系统或模块明确不拥有什么？
- 允许的依赖方向是什么？
- 数据由谁拥有，其他模块如何访问？
- 模块之间如何通信？
- 哪些业务不变量必须始终成立？
- 哪些状态流转允许，哪些禁止？
- 事务边界在哪里？
- 哪些操作必须幂等？
- 外部系统失败时如何处理？
- 授权在哪里执行？
- 未来开发者应该避免什么？
- 常见变更应该怎样做？
- AI Coding agent 修改代码前必须读什么？

收敛检查：

- 删除一节后，未来修改是否仍然安全？如果是，删掉或改成引用。
- 这段是否只是 API、事件、字段、文件或调用链说明？如果是，删掉。
- 这段是否只在解释“代码现在怎么写”，而不是“为什么必须这样写”？如果是，删掉。
- 这条规则是否有 owner、边界、禁止事项或失败后果？如果没有，补充或删除。

差的架构文档通常有这些问题：

- 描述每个文件，但没有设计规则。
- 重复代码，而不是解释约束。
- 把 API 文档、事件清单或目录树搬进架构文档。
- 没有禁止事项。
- 没有数据所有权。
- 忽略事务、幂等、失败处理或安全。
- 记录理想架构，而不是当前代码真实遵循的架构。

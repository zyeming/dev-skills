# 需求文档编写

## 目标与边界

创建或维护一份供产品、研发和测试共同确认的 Markdown 需求文档。文档回答本期为什么做、覆盖什么、用户如何使用、系统遵循什么规则，以及还有什么尚未决定。

需求文档不决定数据库结构、完整接口契约、代码落点、实施顺序或发布方案，也不修改业务代码。用户要求技术设计、实施计划或代码实现时，完成当前需求文档任务后停止，除非用户明确要求继续。

## 工作模式

- **新建**：根据用户说明、原型、issue、现状资料和必要源码创建需求文档。
- **更新**：将最新确认结论放入唯一归属位置，更新相关引用并删除失效表述。
- **精简**：保持已确认语义不变，合并重复内容并明确章节职责。
- **评审**：检查完整性、歧义、矛盾、重复和可验证性；用户说“先别改”时只报告，不修改文件。

用户指定路径、章节或既有格式时优先遵守；否则使用本技能模板。

## 事实与决策来源

按以下优先级判断信息用途：

1. 用户最新明确确认的结论决定目标需求和业务口径。
2. 用户指定的原型、issue、会议结论和已批准需求说明目标意图；冲突时请求澄清。
3. 源码、配置、schema 和测试决定当前行为；既有文档与源码冲突时指出文档漂移。
4. `AGENTS.md`、`CLAUDE.md` 和项目规则决定调查方式、文档位置与允许操作。
5. 既有文档只用于导航、术语和背景，不能覆盖最新用户决策或当前代码证据。

不得把目标设想写成当前事实，也不得用当前实现否定用户已确认的目标变化。

## 工作流程

1. 读取项目规则、用户提供的全部材料、现有需求和相关现状说明。
2. 需要描述当前行为或沿用现有规则时，沿真实入口、路由、接口、配置和数据流核验到规则实际生效或被使用的位置，并区分名称相近但作用不同的条件、字段或权限。
3. 整理目标、参与者、范围、功能需求、业务规则、非功能需求、业务图示、当前行为和来源。
4. 将内容分为已确认需求、待确认业务问题、与本需求直接相关的非本期内容和技术设计问题。
5. 对影响范围、用户行为、状态、时间、通知、权限、数量、统计或验证口径的未知事项集中澄清。每题只问一个决策，并给出明确推荐；能从材料或源码查明的事实不提问。
6. 用户暂不决定或要求先出草稿时继续成稿，将未决业务问题集中记录为 `OPEN-*`，不得用推荐方案替代用户决定。
7. 新建、更新或精简时完整读取 [需求文档模板](references/requirements-document-template.md)；评审和交付前完整读取 [Review Checklist](references/requirements-document-review-checklist.md)。
8. 完成后检查编号、引用、术语、Markdown、Mermaid 和本地链接，然后交付并停止。

## 内容唯一归属

每个已确认结论只有一个正文归属，其他位置只引用编号或提供必要上下文：

| 内容 | 唯一归属 |
| --- | --- |
| 业务问题、目标结果和总体边界 | 需求概述 |
| 覆盖与排除的场景、终端和工程 | 需求范围 |
| 用户能做什么、系统如何响应 | 功能需求 |
| 状态、权限、时间、数量、通知、统计和历史数据处理口径 | 业务规则与约束 |
| 性能、可靠性、安全、审计、终端或版本兼容和可观测性指标 | 非功能需求 |
| 尚未形成决策的业务问题 | 待定内容 |
| 当前系统行为及结论证据 | 现状与参考资料 |

- 同一需求或规则只完整说明一次。功能需求引用业务规则编号，不复制规则正文。
- 功能需求、业务规则和非功能需求必须自包含、清楚、明确、可验证；熟悉业务但未参与讨论的读者无需查阅源码即可判断具体场景的结果。
- 业务规则涉及多个对象、条件、优先级或例外时，展开必要分支和条件关系，不用概括代替具体规则。
- 默认不生成独立的“验收标准”章节。
- 当前规则若继续作为目标约束，在目标章节标记为“现有沿用”；现状章节只提供证据和编号引用。
- 来源说明证据支持哪些编号，不重新复述需求正文。

## 目标表达与范围边界

- 需求概述、功能需求和业务规则默认正向说明本期提供的能力、适用条件和系统结果。能够从正向规则直接推导出的反面，不另写成需求。
- “非本期范围”只收录与本需求直接相邻且容易被误认为本期范围的内容：原型、Demo 或原始需求中出现的模块；已纳入模块中明确延后的子功能；需要通过当前方案与目标方案对比才能说清的能力边界。
- 普通未受影响模块、通用技术工作、与本需求关系不大的能力，不为说明“本期不做”而列入文档。
- 非本期范围之外的否定性表述，只有在它决定用户可见结果、业务规则或当前与目标差异时才保留，并写清触发条件和依据。
- 当前方案与目标方案存在差异时，只在最自然的归属位置完整对比一次，其他章节引用对应编号或边界。

## 文档状态

- 默认状态为“需求草稿”。存在任何未决业务问题时必须保留“待定内容”。
- 只有不存在待定项且用户明确确认文档或全部需求时，才标记为“需求确认稿”。
- 待定项使用稳定编号 `OPEN-01`、`OPEN-02`。问题解决后，将结论移入唯一归属章节，更新引用并删除对应待定项。

## 输出约束

- 使用稳定编号；区分“现有沿用”“本期新增”“本期调整”。
- Figma 或用户提供的图示能够清楚表达业务时，优先直接使用，不重复绘制等价图；与已确认需求存在尚未解决的冲突时，先请用户确认。
- 没有合适图示且图能明显降低理解成本时，才绘制用例图、流程图或状态图；图不得引入正文未确认的行为。
- 非功能需求只在存在明确质量要求时保留，并写成可度量、可验证的要求；不得虚构指标。
- 删除空章节、分析过程、重复结论、已解决的澄清过程和无业务价值的工程细节。
- 默认输出到 `docs/requirements/{ticket-id-or-date}-{feature-name}.md`；项目已有需求目录时沿用项目规则。

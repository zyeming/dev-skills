# 需求文档编写

## 目标

为单个软件或产品需求创建、评审、精简或更新一份可供产品、研发和测试共同确认的需求文档。

需求文档回答“本期为什么做、做什么、怎样表现、哪些规则必须遵守、怎样验收”。它不决定数据库结构、接口设计、代码落点或实施顺序，也不修改业务代码。

## 工作模式

根据用户指令选择模式，不要求用户声明模式名称：

- 新建：根据聊天、原型、issue、现状资料和必要的源码创建需求文档。
- 评审：检查完整性、歧义、矛盾、重复和不可验收内容；用户说“先别改”时只报告，不修改文件。
- 精简：保留已确认语义，合并重复内容，明确章节分工并提高可读性。
- 更新：把最新确认结论归入正确章节，同步用例图、验收标准和来源，删除失效表述。

用户指定输出路径、章节或既有格式时优先遵守；否则使用本技能的默认模板。

## 输入与事实来源

按以下规则判断信息用途，不给单一材料无限权威：

- 当前用户明确确认的结论决定目标需求、范围和验收口径；较新的确认覆盖较旧的产品表述。
- `AGENTS.md`、`CLAUDE.md` 和项目规则决定调查方式、允许操作和文档位置。
- 用户指定的原型、issue、会议结论和已批准需求是目标需求的来源；材料冲突时请求用户澄清。
- 当前源码、配置、schema 和测试决定系统现在怎样；需求文档或现状说明与源码冲突时，指出文档漂移。
- 既有文档用于导航、术语和背景，不能替代最新用户决策或当前代码证据。

始终区分“当前行为”和“目标需求”。不要把目标设想写成当前事实，也不要用当前实现否定用户已确认的目标变化。

## 工作流程

1. 读取项目规则、用户提供的全部材料、现有需求和相关现状说明。需要描述当前行为或判断工程范围时，沿真实入口、路由、接口、配置和数据流做最小充分的源码核验。
2. 整理目标、参与者、业务场景、范围、用户可见行为、业务规则、验收口径、当前行为和来源。
3. 将信息分成：已确认需求、待确认业务问题、明确非本期内容、只属于技术设计的问题。不要把技术实现选择升级成产品待定项。
4. 对影响业务范围、用户行为、状态、时间边界、通知渠道、权限、统计口径或验收的问题，一次性向用户澄清。每题只问一个决策，给出 2—4 个互斥选项和明确推荐；能从材料或源码查明的事实不提问。
5. 用户完成决策后再写入正式需求。用户明确“暂不确定”“先出草稿”或拒绝决定时，继续生成草稿，并按“待定内容”规则记录；不得用推荐方案填充未确认的产品语义。
6. 新建、精简或更新时读取 `references/requirements-document-template.md`；评审和交付前读取 `references/requirements-document-review-checklist.md`。
7. 完成后检查章节职责、需求编号、用例图、待定项、验收追踪、术语、Markdown、Mermaid 和本地链接。输出结果后停止，不继续编写 Technical Design、Implementation Plan 或业务代码。

## 文档状态与待定内容

- 默认状态为“需求草稿”。只有不存在待定项且用户明确确认文档或全部需求时，才标记为“需求确认稿”。
- 存在任何未决业务问题时，状态必须保持“需求草稿”，并保留“待定内容”章节。
- 使用稳定编号 `OPEN-01`、`OPEN-02`。每项只记录待定问题、已确认边界、影响范围和推荐方案。
- 正式章节只写已确认事实。需要关联时仅引用 `OPEN-*`，不要在多个章节重复展开待定问题。
- 用户后续确认后，将结论移入其唯一归属章节，同步相关需求编号和验收标准，再删除对应 `OPEN-*`。
- 最后一个待定项解决后，删除整个“待定内容”章节并重新连续编号。

## 内容唯一归属

| 内容 | 唯一归属 |
| --- | --- |
| 为什么做、解决什么问题、总体结果 | 需求概述 |
| 本期覆盖和排除哪些业务场景、终端与工程 | 需求范围 |
| 用户能做什么、系统怎样表现 | 功能需求 |
| 时间、状态、权限、数量、通知和统计口径 | 业务规则与约束 |
| 怎样证明需求完成 | 验收标准 |
| 尚未形成决策的业务问题 | 待定内容 |
| 当前系统怎样、结论依据是什么 | 现状与参考资料 |

同一规则只完整说明一次。功能需求使用稳定主题编号，例如 `IMG-01`、`PAT-01`；验收标准引用编号并描述可观察结果，不重新复制整条需求。删除没有信息价值的空章节、重复结论和分析过程。

## 用例图规则

“相关用例图”默认必需，固定放在“需求概述”之后，作为全篇业务用例总览。确实不存在有意义的参与者交互时，可以省略，但必须在交付说明中写明原因。

- 使用单张 Mermaid `flowchart`。参与者放在范围外，核心业务用例放入 `subgraph scope["本期用例范围"]`。
- 默认不超过 4 个参与者、8 个核心用例；超过时合并相近用例，不增加第二张总览图。
- 每个用例只表达一个业务目标，使用动宾短语，节点文字最多两行。
- 只展示参与者、核心业务用例和必要的触发或依赖关系；不展示仓库、接口、数据库、DTO、内部服务或完整状态流转。
- 不使用复杂颜色、样式、图例或装饰节点；不在同一节点用斜杠堆叠不同角色的行为。
- 只画已确认用例。未确定行为进入 `OPEN-*`，不得在图中表现为已确认事实。
- 图必须与需求范围、功能需求和验收标准一致；正文是事实来源，发现不一致时修改图。

评审时检查 Mermaid 围栏成对、节点标识唯一、箭头关系可解释、文字密度可读，并确认图只起总览作用。

## 文档规格

默认结构为：

1. 文档信息
2. 需求概述
3. 相关用例图
4. 需求范围
5. 功能需求
6. 业务规则与约束
7. 验收标准
8. 待定内容（仅存在待定项时保留）
9. 现状与参考资料

没有待定项时删除第 8 节，“现状与参考资料”顺延为第 8 节。模板是默认结构；用户或项目明确要求保留既有章节时，保持其结构并应用相同的内容归属和质量规则。

默认输出到：

```text
docs/requirements/{ticket-id-or-date}-{feature-name}.md
```

项目已有需求目录时沿用现有目录。文件名使用小写 kebab-case；有 ticket id 时优先使用 ticket id。

## 不要写

- 未经确认的产品语义、伪造的当前行为或无法追溯的结论。
- 数据库 schema、完整接口字段、代码任务、实施顺序和测试代码。
- 重复的 `Confirmed Decisions`、同义需求清单或逐字复述功能需求的验收标准。
- 为了填满模板创建的空章节、装饰性图表和没有业务价值的工程细节。
- 已经解决的澄清过程；只保留最终结论和仍然有效的待定项。

## 与其他 Skill 的关系

- 只需要对话式梳理、还不准备形成文档时，使用 `$requirements-clarification`。
- 需要创建、评审或更新持久化需求文档时，使用本技能；本技能自行处理必要澄清，不要求切换 Skill。
- 需求确认后需要设计数据模型、前后端接口和关键实现方案时，使用 `$technical-design-writing`。
- 目标方案确认后需要 Coding Agent 可执行计划时，使用 `$implementation-plan-writing`。

除非用户明确继续要求，否则交付需求文档或评审结果后停止。

# 需求文档 Review Checklist

检查目标是让产品、研发和测试对“做什么、边界是什么、怎样验收、还有什么未决定”形成同一理解。只检查与实际需求有关的项目，不为覆盖清单增加空内容。

## 目标与来源

- [ ] 需求解决的问题、参与者、目标结果和核心边界清楚。
- [ ] 最新用户确认决定目标需求，旧结论没有覆盖新决策。
- [ ] 当前行为由源码、配置、schema、测试或可信现状文档支持。
- [ ] 当前行为与目标需求分开，目标变化没有写成当前事实。
- [ ] 原型、用户确认和代码证据分别说明支持了什么判断。
- [ ] 需求文档没有越界决定数据库 schema、完整接口契约或实施步骤。

## 范围与完整性

- [ ] 业务场景范围、工程范围和非本期范围职责清楚，没有互相重复。
- [ ] 正常流程、异常结果和关键边界场景已覆盖。
- [ ] 相关的状态、时间、时区、数量、格式、通知、权限、统计和历史兼容口径已说明。
- [ ] “成功”“完成”“送达”“已查看”“已确认”等容易混淆的概念有唯一含义。
- [ ] 没有提前加入本期不需要的终端、角色、状态或扩展能力。

## 功能需求与规则

- [ ] 功能需求使用稳定主题编号，每项只表达一个主要行为。
- [ ] 用户可见行为位于功能需求，跨功能边界位于业务规则与约束。
- [ ] 同一业务规则只完整出现一次，其他章节通过编号或适用范围引用。
- [ ] 默认值、触发条件、截止边界、禁用条件和失败结果明确。
- [ ] 旧记录、重复操作、幂等、权限和未授权结果在相关时得到说明。
- [ ] 文档没有保留重复的 `Confirmed Decisions` 或同义需求清单。

## 相关用例图

- [ ] 用例图位于需求概述之后，并能作为全篇总览。
- [ ] 默认使用单张 Mermaid `flowchart`；确实省略时交付说明给出合理原因。
- [ ] 参与者位于范围外，核心用例位于“本期用例范围”内。
- [ ] 参与者不超过 4 个、核心用例不超过 8 个；超出内容已合并为更高层业务用例。
- [ ] 每个用例是单一动宾目标，节点文字不超过两行。
- [ ] 图中没有仓库、接口、数据库、DTO、内部服务、完整状态流转或装饰节点。
- [ ] 同一节点没有用斜杠堆叠不同角色行为。
- [ ] 图中只包含已确认用例，没有把 `OPEN-*` 或推荐方案画成事实。
- [ ] 节点标识唯一、箭头关系可解释、Mermaid 围栏成对。
- [ ] 图与需求范围、功能需求、业务规则和验收标准一致。

## 验收追踪

- [ ] 每项核心功能和关键业务规则至少有一个验收场景覆盖。
- [ ] 验收标准引用真实需求编号，不引用已删除或待定编号。
- [ ] 验收结果可观察、可判定，包含必要前置条件和边界。
- [ ] 验收标准没有逐字复制全部功能需求，也没有引入新需求。
- [ ] 正向、禁用、过期、重复操作、权限和兼容场景在相关时得到覆盖。

## 待定内容与状态

- [ ] 影响范围、用户行为、状态、时间、通知、权限、统计或验收的未知内容已向用户澄清。
- [ ] 能从材料或源码确认的事实没有被错误列为待定问题。
- [ ] 技术实现选择没有被错误列为产品待定问题。
- [ ] 用户暂不决策的事项使用稳定 `OPEN-*` 集中记录。
- [ ] 每个待定项只问一件事，并写明已确认边界、影响范围和推荐方案。
- [ ] 推荐方案没有写成已确认事实，正式章节没有重复展开待定问题。
- [ ] 存在待定项时文档状态为“需求草稿”。
- [ ] 已解决待定项已回填唯一归属章节、同步验收并删除；没有待定项时整节已删除。
- [ ] 只有无待定项且用户明确确认时，文档状态才是“需求确认稿”。

## 可读性与格式

- [ ] 一级章节顺序和编号连续；删除可选章节后后续编号已顺延。
- [ ] 标题、术语、角色、入口和状态名称全文一致。
- [ ] 表格只用于需要对齐的范围、需求、规则、验收和待定项，正文用于解释结论。
- [ ] 一个段落或列表项只表达一个中心意思，没有连续分号堆叠多个规则。
- [ ] 空章节、分析过程、机械代码清单和没有信息价值的文字已删除。
- [ ] Markdown 围栏成对，本地相对链接存在，Mermaid 与正文一致。
- [ ] 熟悉业务但没参与讨论的读者可以说清目标、范围、关键规则、验收方式和剩余待定事项。

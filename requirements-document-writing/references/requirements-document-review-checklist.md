# 需求文档 Review Checklist

检查目标是让产品、研发和测试对“为什么做、做什么、遵循什么规则、还有什么未决定”形成同一理解。只检查与实际需求有关的项目，不为覆盖清单增加空内容。

## 目标、范围与来源

- [ ] 业务问题、参与者、目标结果和核心边界清楚。
- [ ] 最新用户确认决定目标需求，旧结论没有覆盖新决策。
- [ ] 当前行为由源码、配置、schema、测试或可信现状文档支持。
- [ ] 描述现有规则时已核验到规则实际生效或被使用的位置，没有混淆名称相近但作用不同的条件、字段或权限。
- [ ] 当前行为、目标需求、推荐方案和待定问题没有混写。
- [ ] 原型、用户确认和代码证据说明其支持的需求或规则编号，没有重复需求正文。
- [ ] 本期范围正向说明覆盖场景和能力；非本期范围没有混入目标功能或规则。
- [ ] 每个非本期项都能追溯到原型、Demo、原始需求、当前相邻能力或用户确认，并且确实容易被误认为本期范围。
- [ ] 普通未受影响模块、通用技术工作和与本需求关系不大的能力没有被列为非本期内容。
- [ ] 非本期范围之外的否定性表述确实决定用户可见结果、业务规则或当前与目标差异，不是正向规则可以直接推导出的重复说明。
- [ ] 文档没有越界决定数据库 schema、完整接口契约、代码落点或实施步骤。

## 单一归属与编号

- [ ] 每个已确认结论只有一个完整定义位置，其他章节只引用编号或提供必要上下文。
- [ ] 功能需求只定义用户可见行为；跨功能状态、权限、时间、数量、通知、统计和历史数据处理口径位于业务规则。
- [ ] 功能需求和业务规则使用稳定且真实存在的编号，引用没有指向已删除内容。
- [ ] “现有沿用”“本期新增”“本期调整”标记与当前代码和目标变化一致。
- [ ] 当前沿用规则完整定义在目标章节；现状章节只提供证据和编号引用。
- [ ] 当前方案与目标方案的差异只完整说明一次，其他位置通过编号或边界引用。
- [ ] 文档没有重复的决策清单、同义需求、完整规则副本或机械总结。

## 功能需求与业务规则

- [ ] 每条功能需求只表达一个主要行为，并写清必要的触发条件、操作和系统结果。
- [ ] 每条业务规则完整表达一个业务口径；未参与讨论的读者无需查阅源码即可判断具体场景的结果。
- [ ] 涉及多个对象、条件、优先级或例外时，必要分支和条件关系完整清楚，没有用概括代替具体规则。
- [ ] 每条功能需求和业务规则都明确、可判定，并能直接转成测试用例。
- [ ] 默认值、禁用条件、重复操作、幂等、权限、并发冲突和历史数据处理在相关时得到说明。
- [ ] “成功”“完成”“送达”“已查看”“已确认”等容易混淆的概念具有唯一含义。
- [ ] 未经确认的产品语义没有作为正式需求写入。

## 非功能需求

- [ ] 仅在存在明确系统质量要求时保留非功能需求章节。
- [ ] 性能、可靠性、安全、审计、终端或版本兼容和可观测性要求具有适用条件、量化指标和验证口径。
- [ ] 无法确认的指标进入 `OPEN-*`，没有使用“性能良好”“安全可靠”等不可验证表述。
- [ ] 业务权限和状态规则没有被误写成非功能需求，技术实现方案没有被误写成质量要求。

## 业务图示

- [ ] 仅在图能明显降低理解成本时保留图示，简单需求没有机械生成图表。
- [ ] Figma 或用户提供的合适图示已优先直接使用；同一流程没有重复绘制信息等价的图，通常不超过两张。
- [ ] 图示与已确认需求的冲突已经用户确认，没有自行选择冲突口径。
- [ ] 多角色或能力边界使用用例图；多步骤、分支或角色交接使用流程图；复杂生命周期使用状态图。
- [ ] 图只包含已确认的角色、步骤、分支和状态关系，没有接口、数据库、DTO 或内部服务细节。
- [ ] 图中没有把 `OPEN-*`、推荐方案或推测行为画成已确认事实。
- [ ] 图与对应需求和规则编号一致；图片链接有效，Mermaid 围栏成对、节点唯一、箭头可解释。

## 待定内容与文档状态

- [ ] 影响范围、用户行为、状态、时间、通知、权限、数量、统计或验证口径的未知内容已集中澄清。
- [ ] 能从材料或源码确认的事实没有被错误列为待定问题。
- [ ] 技术实现选择没有被错误列为产品待定问题。
- [ ] 用户暂不决策的事项使用稳定 `OPEN-*`，每项只问一个决策并写明影响范围。
- [ ] 推荐方案没有进入正式需求，正式章节只通过编号引用待定项。
- [ ] 存在待定项时文档状态为“需求草稿”；全部解决且用户确认后才标记为“需求确认稿”。
- [ ] 已解决待定项已移入唯一归属章节并删除，相关引用已同步更新。

## 可读性与格式

- [ ] 可选章节只在有内容价值时保留，一级章节重新连续编号。
- [ ] 标题、术语、角色、入口和状态名称全文一致。
- [ ] 表格只用于需要对齐的信息，正文用于解释结论。
- [ ] 一个段落、列表项或表格行只表达一个中心意思，没有连续分号堆叠多条规则。
- [ ] 空章节、分析过程、已解决的澄清过程和无业务价值的工程细节已删除。
- [ ] Markdown、本地链接和 Mermaid 均有效。
- [ ] 熟悉业务但未参与讨论的读者能够说清目标、范围、关键功能、关键规则和剩余待定事项。
